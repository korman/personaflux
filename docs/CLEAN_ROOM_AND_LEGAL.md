# 独立实现与法律边界

## 基本立场

PersonaFlux 是受公开情感理论和社会模拟理念启发的独立实现，不是 Love/Hate 的源码移植、Rust 翻译或官方替代品。

本文是工程风险控制指南，不构成法律意见。发布前必须核对参考项目实际许可证，并在必要时咨询专业律师。

## 可以独立实现的内容

- PAD 等公开理论。
- 阵营、有向关系、行为、记忆、信任和传闻等抽象概念。
- 团队自行撰写的输入输出行为规格。
- 自行设计的 API、架构、测试和示例。

源码可见不代表可以移植或再发布具体实现。

## 禁止默认执行

- 逐行或近似逐行翻译 C# 源码。
- 复制代码结构、注释、文档、示例文本和默认数据。
- 复用原资源、图标、编辑器布局或示例资产。
- 使用 Love/Hate 品牌或暗示官方关系。
- 在未核实许可证前发布来自原程序的兼容测试数据。

## 推荐流程

1. 从公开理论和产品目标写原创领域定义。
2. 将期望行为写成中立输入输出规格。
3. 为规格创建原创测试向量。
4. 仅根据规格实现 Rust 代码。
5. 使用独立名称、默认值、示例和文档。
6. 对公式记录公开来源或原创推导。
7. 发布前复核许可证和商标。

## 兼容层次

- 概念兼容：PAD、阵营、关系、行为、记忆和传闻等概念相近。
- 行为兼容：对已定义规格的输入产生稳定输出。
- API 兼容：复制类名、方法和序列化格式。

PersonaFlux 追求前两项中的原创规格稳定，不追求 Love/Hate API 或存档兼容。

## 品牌与许可证

- 不使用 `LoveHate`、`OpenLoveHate` 等易造成关联的名称。
- README 必须明确 `independent implementation`。
- 发布前检查 GitHub、crates.io、包仓库、域名和商标。
- 当前仓库使用 MIT License。未来如改为双许可证，必须同步添加完整的 Apache-2.0 许可证文件，并确保没有混入冲突材料。
